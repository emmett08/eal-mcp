# From a claim to an accountable assessment

An engineering claim becomes useful when another engineer can examine why it
holds, where it applies and what would change the conclusion. EAL represents
those relationships in source and executes the evidence requests needed to assess
them. The resulting record connects the claim to the exact source, context,
measurements and method implementations used in that assessment.

Consider a proposal to parallelise CI test groups. Shorter elapsed time is only
part of the claim. The comparison also needs to preserve the intended workload
and test outcomes. A timing observation, an equivalence check and a review of
independence answer different questions. EAL keeps those obligations separate
while allowing the claim to depend on all of them. A computation can check a
specified relationship. Its applicability to the pipeline still needs evidence.

The normal execution package has three parts: `case.eal` defines the argument
and acquisition dependencies, `tools.toml` selects concrete operations and
permissions, and any custom implementations live beside them. The runtime
collects observations and evaluates the argument under those choices. EngArg can
help author the package, while EAL executes it independently.

## Run one complete argument

Begin with [installation and a first run](getting-started.md). The guide uses a
synthetic finite inventory so the observation, calculation and deductive step are
small enough to inspect. It runs the installed MCP host and then shows how to
retain the collection and inspect its assessment separately.

Once that path works, [executable programmes](executable-programs.md) explains
how the same mechanism handles measured inputs, pure calculations and scoped
reviews. The [language reference](language-v4.md) defines what the declarations
mean. The finite example demonstrates execution mechanics. Claims about an
actual CI pipeline require observations from that pipeline and a justified
comparison design.

## Connect the programme to the system being investigated

Use [direct tool manifests](direct-tools.md) to select an existing command, MCP
operation, HTTP endpoint or retained observation. The manifest fixes access and
transport. The argument fixes the evidence requirement. Keeping those decisions
separate makes it possible to review a programme before granting it access.

The [collector guide](collectors.md) introduces the acquisition envelope and
shows how to write a collector. [API and delivery evidence](api-collectors.md)
then covers telemetry, GitHub CI and imported reports. The
[deployment example](catalog-sync-operator.md) applies those boundaries to a
named Kubernetes resource and a bounded Tempo search. These specialised adapters
are useful when their source contracts match the investigation.

When an operation is missing, [portable tool packages](tool-packages.md) explains
how EAL executes a verified implementation generated by EngArg. The
[collector authoring contract](collector-contracts.md) is the reference for
clients that choose to discover optional native collector descriptions.

## Interpret the result and retain the decision basis

Collection records what a tool returned. Assessment asks whether those records
satisfy the declared predicates, freshness rules, assumptions and inference
requirements. A measured negative can defeat support. An acquisition failure
leaves the measurement unavailable. Both outcomes must remain visible to the
engineer deciding what to do next.

[Runtime ownership](runtime.md) explains the clocks, identities, budgets and
process supervision that preserve this distinction. [Applications and MCP
hosting](applications.md) covers staged execution, transport configuration and
optional registered claims for repeated assessment. [Packets](packets.md)
explains how to share bounded results while retaining links to the full record.

Where the question requires finite argumentation semantics, use
[ASPIC reasoning and visualisation](aspic.md). Its explicit formal result is
retained beside the authored EAL assessment so the two can be interpreted on
their own terms.

## Coordinate work and change the implementation

For a durable assessor/reviewer workflow, continue with
[coordination](coordination.md). [Tickets](tickets.md) covers the application
handoff from authoring through exported-package execution. Both paths retain
effect ownership and recovery state, which matter when a worker stops after an
external operation may already have occurred.

Contributors should read [implementation boundaries](implementation.md), then
[interface contracts](interface-contracts.md) and [method execution](method-execution.md)
for the boundary they intend to change. [Published schemas](contracts.md) points
to the canonical machine-readable definitions. [Development and verification](development.md)
gives the build, parser-regeneration and installed-acceptance commands.

The [context experiment](context-experiment.md) is a separate
research record with its own commands and evidence labels. Its synthetic
rehearsals and prospective calculations do not establish production model-quality
effects.
